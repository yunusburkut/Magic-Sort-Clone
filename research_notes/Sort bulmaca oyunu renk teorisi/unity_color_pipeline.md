# Unity 6 URP 2D color pipeline: putting a designed sRGB/OKLCH palette on screen accurately (Linear color space)

Scope: Unity 6 (6000.x), URP 17 2D Renderer, Linear color space, SpriteRenderer plus custom HLSL shaders. Researched October 2026. Version-specific or dated guidance is flagged inline.

Project snapshot (read from the repo, not from a web source; useful context for the report writer):
- `ProjectSettings.asset`: `m_ActiveColorSpace: 1` (Linear).
- `Assets/Settings/UniversalRP.asset`: `m_SupportsHDR: 1`, `m_ColorGradingMode: 0` (LDR grading), `m_ColorGradingLutSize: 32`.
- `SampleScene.unity` camera: `m_RenderPostProcessing: 0` (post-processing off, so no tonemapping/LUT pass runs today).
- `TubeLiquid.cs` converts layer colors with `.linear` before `MaterialPropertyBlock.SetVectorArray("_LayerColors")`. `PourStreamView.cs` writes `color.linear` into mesh vertex colors. `TubeGlass.shader` uses `Blend One OneMinusSrcAlpha` with a premultiplied sprite whose rgb/alpha were derived from linear EXR renders (`Tools/AssetGen/make_assets.py`, `render_tube`). `Liquid.shader`'s `Grade()` computes luma with `half3(0.299, 0.587, 0.114)` on linear values.

## Q1. How should a hex color from a design spec be entered so the rendered pixel matches it (Inspector Color fields, `Color` in C#, shader properties, vertex color via SpriteRenderer)?

### Takeaway
Type the designer's sRGB hex as-is into anything Unity treats as a "color": Inspector color pickers, `Material`/`MaterialPropertyBlock.SetColor`, `SpriteRenderer.color`, Shader Graph Color (Default mode). In a Linear project Unity linearizes these on upload, and the sRGB framebuffer re-encodes them, so an unlit, untonemapped, opaque pixel comes back as the same hex (within 8-bit rounding). Raw channels are not converted: `SetVector`, `SetVectorArray`, `SetColorArray`, mesh vertex colors you write yourself, and hard-coded HLSL constants. For those, convert with `Color.linear` in C# or `SRGBToLinear()` in HLSL. Keep palette colors off `[HDR]` properties.

### Cited Findings
- Unity 6 Linear color space manual: "For colors, this conversion is applied implicitly, because the Unity Editor already converts the values to floating point before passing them to the GPU as constants." When textures are sampled, "the GPU automatically removes the gamma correction". On output, the result "is either gamma-corrected straight away or left in linear space for later gamma correction"; with HDR, "rendering results are left in linear space and gamma corrected later." — [Unity Manual 6000.2: Linear color space](https://docs.unity3d.com/6000.2/Documentation/Manual/linear-color-space.html)
- The same page says Unity uses the GPU's sRGB sampler by default to cross from gamma to linear, and textures authored in linear space need sRGB sampling bypassed (the sRGB (Color Texture) import flag). — [Unity Manual 6000.2: Linear color space](https://docs.unity3d.com/6000.2/Documentation/Manual/linear-color-space.html)
- ShaderLab `[Gamma]` attribute: "Indicates that a float or vector property uses sRGB values, which means that it must be converted along with other sRGB values if the color space in your project requires this." `[HDR]`: "For color properties, the Unity Editor uses the HDR color picker." A `Color` property "maps to a float4". — [Unity Manual 6000.2: Shader properties](https://docs.unity3d.com/6000.2/Documentation/Manual/SL-Properties.html)
- `MaterialPropertyBlock.SetColor` (6000.2): "The method assumes that the color value is in sRGB space. The method converts the value to linear color space if the active project color space is linear." It "does not support setting HDR colors directly"; for HDR, use `SetVector` with the RGB components holding the HDR color. Switching color spaces does not convert stored values automatically. — [Unity Scripting API: MaterialPropertyBlock.SetColor](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/MaterialPropertyBlock.SetColor.html)
- `Material.SetColorArray`: "It is just an alias to SetVectorArray, only colors are cast to vectors. No sRGB-linear conversion is done during the function call." — [Unity Scripting API: Material.SetColorArray](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Material.SetColorArray.html)
- **Documentation conflict:** the 6000.2 `Material.SetColor` page says a property counts as gamma space (and is converted to linear in a Linear project) only if it is "declared as a color and has the [HDR] attribute" or "declared as a color or vector and has the [Gamma] attribute", and "Otherwise, value is stored without modification." — [Unity Scripting API: Material.SetColor](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Material.SetColor.html). This contradicts the implicit color conversion in the [Linear color space page](https://docs.unity3d.com/6000.2/Documentation/Manual/linear-color-space.html) and the sRGB assumption in [MaterialPropertyBlock.SetColor](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/MaterialPropertyBlock.SetColor.html).
- `Color.linear`: "A color value in linear space converted from an sRGB value." — [Unity Scripting API: Color.linear](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Color-linear.html). `Mathf.GammaToLinearSpace` "Converts the given value from gamma (sRGB) to linear color space." — [Unity Scripting API: Mathf.GammaToLinearSpace](https://docs.unity3d.com/530/Documentation/ScriptReference/Mathf.GammaToLinearSpace.html)
- Shader Graph Color node, Default mode, generates `IsGammaSpace() ? float4(c) : float4(SRGBToLinear(c.rgb), a)`, so Default colors are treated as sRGB and linearized. **Old-version flag:** "In versions prior to 10.0, Shader Graph assumed that HDR colors from the Color Node were in gamma space. Version 10.0 corrected this behavior, and Shader Graph now interprets HDR colors in linear space." — [Shader Graph 17.0: Color Node](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Color-Node.html). Color property modes: "Default: Allows to select a standard sRGB color. HDR: Allows to select an HDR color and sets its intensity from -10 to 10 exposure stops." — [Shader Graph 17.0: Property Types](https://docs.unity3d.com/Packages/com.unity.shadergraph@17.0/manual/Property-Types.html)
- `SpriteRenderer.color` is the "Rendering color for the Sprite graphic... The selected vertex color becomes the rendering color, and is accessible in a pixel shader." No color space is stated. — [Unity Scripting API: SpriteRenderer.color](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/SpriteRenderer-color.html)
- URP's default sprite shaders apply the renderer color with no gamma conversion: `o.color = input.color * _Color * unity_SpriteColor;` (Sprite-Lit-Default, Sprite-Unlit-Default). In `Core2D.hlsl`, `unity_SpriteColor` maps to the instanced `unity_SpriteRendererColorArray`, commented "SpriteRenderer.Color while Non-Batched/Instanced". — [Unity Graphics repo: Sprite-Lit-Default.shader](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.universal/Shaders/2D/Sprite-Lit-Default.shader), [Sprite-Unlit-Default.shader](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.universal/Shaders/2D/Sprite-Unlit-Default.shader), [Core2D.hlsl](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.universal/Shaders/2D/Include/Core2D.hlsl)
- Spine runtime issue: in Linear, custom vertex-color tinting must convert vertex colors gamma→linear or "the colors set in the Unity Editor UI ... won't match the rendered tint". The reporter observed that "Unity SpriteRenderers (?) already compensate for this somehow" because Sprites/Default does no extra color processing. Fix: `GammaToLinearSpace(rgb)` when `UNITY_COLORSPACE_GAMMA` is not defined, alpha untouched (closed March 2021). — [EsotericSoftware/spine-runtimes #1301](https://github.com/EsotericSoftware/spine-runtimes/issues/1301)
- Unity Discussions (tagged 6.2, Sept 2025, community answer, no Unity staff reply): vertex colors carry no color-space tag, unlike textures with their importer setting, so the developer must decide. In a Linear project, gamma-authored vertex colors need conversion; the suggested fix is a Custom Function node that checks the color-space macro. — [Unity Discussions: Vertex color not linear in shader graph?](https://discussions.unity.com/t/vertex-color-not-linear-in-shader-graph/1684171)
- A forum answer says Unity 2023+ lets you control whether the sprite color is applied in Shader Graph sprite targets. This is a secondary source summarized by search. — [Unity Discussions: How is a sprite color passed to the shader graph?](https://discussions.unity.com/t/how-is-a-sprite-color-passed-to-the-shader-graph/801363)
- UI only: `Canvas.vertexColorAlwaysGammaSpace` keeps Canvas vertex colors in gamma space "before passing to the UI shaders in linear color space work flow", so the gamma-to-linear conversion "happen[s] in UI shaders, where colors have higher precision." — [Unity Scripting API: Canvas.vertexColorAlwaysGammaSpace](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Canvas-vertexColorAlwaysGammaSpace.html)
- The gamma workflow is still documented in Unity 6.3 LTS and 6.4. Only the `MaterialProperty.PropFlags.Gamma` scripting enum is obsolete, replaced by `UnityEngine.Rendering.ShaderPropertyFlags`. — [Unity Manual 6.3: Gamma color space](https://docs.unity3d.com/Manual/gamma-color-space.html), [Unity Scripting API: PropFlags.Gamma](https://docs.unity3d.com/ScriptReference/MaterialProperty.PropFlags.Gamma.html)

### Inferences
- **Entry-point cheat sheet (Linear project):**

  | Where the color enters | What to pass | Converted by Unity? |
  |---|---|---|
  | Inspector Color field (non-HDR) on a material or SpriteRenderer | design hex as-is | yes, on upload |
  | `SpriteRenderer.color = hexColor` | sRGB `Color` (for example from `ColorUtility.TryParseHtmlString`) | yes, per URP sprite shaders doing no conversion plus the Spine observation (verify, see Gaps) |
  | `MaterialPropertyBlock.SetColor` | sRGB | yes (documented) |
  | `Material.SetColor` (non-HDR Color property) | sRGB | expected yes, but the 6000.2 doc wording conflicts, so verify once |
  | `SetVector`, `SetVectorArray`, `SetColorArray`, `SetGlobalVector` | `hexColor.linear` | no |
  | `Mesh.colors` / `colors32` you write, particle custom data | `hexColor.linear`, or convert in the shader | no |
  | Hard-coded HLSL `half3(...)` constants | linear values, or wrap in `SRGBToLinear()` | no |
  | `[HDR]` Color property or Shader Graph HDR color | avoid for palette colors; intensity is in exposure stops and conversion rules differ by API and version | varies |
  | Textures (sprite PNGs) | sRGB (Color Texture) checked for color art; unchecked for masks and data | yes, by the GPU sRGB sampler |

- The repo already does this correctly for raw paths: `.linear` before `SetVectorArray`, and `.linear` into mesh vertex colors. A custom sprite shader must multiply by `unity_SpriteColor` (as `SpriteSilhouette.shader` does) and should not re-linearize it.
- Do all shader math on linear values, including tint multiplies, lerps and lighting, and let the sRGB framebuffer encode once at the end. Interpolating in sRGB (`Color.Lerp` on hex colors) versus linear gives different midpoints: linear midpoints of two saturated colors look lighter and can look washed. For designer-specified gradients, interpolate in OKLab and convert the endpoints or samples to sRGB, then linear.
- Luma weights: `0.299/0.587/0.114` are the Rec.601 gamma-domain luma weights. On linear values, Rec.709/sRGB relative-luminance weights (`0.2126/0.7152/0.0722`) are the physically matching set, which matters for `Grade()`-style saturation tweaks in `Liquid.shader`. This is an inference; the coefficient sources were not fetched in this session.
- Round-trip check: an opaque, unlit, unblended pixel with no tonemapping should read back within ±1/255 of the design hex. Any larger drift points to a double conversion (too dark or too saturated), a missing conversion (too light or washed), lights, post-processing or blending.

### Gaps
- No official Unity statement found that the engine linearizes `SpriteRenderer.color` before it reaches `unity_SpriteColor` or the vertex stream. This is inferred from URP shader source plus the Spine reporter's observation. Validate with a test sprite (white texture, color #808080, unlit, post off), expecting a framebuffer reading of 128.
- The `Material.SetColor` 6000.2 wording (conversion only for `[HDR]`/`[Gamma]`) is unresolved against the other Unity docs. An empirical one-off test is recommended.
- No current source found on how the Unity 6 Inspector HDR color picker's hex field relates to stored linear values.

## Q2. Which URP tonemapping/post settings keep saturated sprite colors true, and what do ACES and Neutral do to pure hues? (Includes 2D Lights / Global Light tinting.)

### Takeaway
For exact palette reproduction, run with post-processing off on the camera, or with Tonemapping = None (no Tonemapping override), Color Adjustments and White Balance at defaults, no Vignette over the play field, and Bloom either off or thresholded so palette colors do not bloom. Draw palette sprites with unlit shaders, or under exactly one white Global Light at intensity 1 with a Multiply blend style. Both tonemappers alter the palette. Neutral maps linear 1.0 to about 0.63, so `#FFFFFF` becomes `#D0D0D0` and pure primaries lose about 18% in sRGB, while mid-tones are roughly preserved. ACES also shifts hues: green becomes yellow-green, cyan becomes paler, purple becomes darker and bluer. It adds contrast too: `#808080` becomes `#696969`.

### Cited Findings
- URP tonemapping modes. None: "Use this option if you do not want to apply tonemapping." Neutral: "range-remapping with minimal impact on color hue & saturation", described as "generally a good starting point for extensive color grading." ACES: "a close approximation of the reference ACES tonemapper, for a more cinematic look. It is more contrasted than Neutral, and has an effect on actual color hue & saturation"; with ACES, "Unity does all the grading operations in the ACES color spaces". — [URP 17 Manual: Tonemapping](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/post-processing-tonemapping.html)
- Neutral tonemapper source: a per-channel rational curve with constants a=0.2, b=0.29, c=0.24, d=0.272, e=0.02, f=0.3, `whiteLevel = 5.3`, `whiteClip = 1.0`. It clamps negative channels to 0 first ("this neutral tonemapper can't deal with them properly (unlike ACES)"). — [Unity Graphics repo: Color.hlsl](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.core/ShaderLibrary/Color.hlsl)
- URP ACES (fitted path, default `TONEMAPPING_USE_FULL_ACES 0`) takes ACES2065-1 input and applies, in order: a "Glow module", a "Red modifier" (`RRT_RED_SCALE 0.82`, `RRT_RED_WIDTH 135`), a "Global desaturation" (`RRT_SAT_FACTOR 0.96`), a fitted RRT+ODT curve, a dim-surround gamma (0.9811), and a second desaturation (`ODT_SAT_FACTOR 0.93`) before converting to Rec.709 primaries. — [Color.hlsl](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.core/ShaderLibrary/Color.hlsl), [ACES.hlsl](https://github.com/Unity-Technologies/Graphics/blob/master/Packages/com.unity.render-pipelines.core/ShaderLibrary/ACES.hlsl)
- URP Grading Mode. "High Dynamic Range: ... Unity applies color grading before tonemapping." "Low Dynamic Range: This mode follows a more classic workflow. Unity applies a limited range of color grading after tonemapping." With the HDR toggle on, "the brightest part of the image can be greater than 1." — [URP 17 Manual: URP Asset](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/universalrp-asset.html)
- Bloom. Threshold: "Set the gamma space brightness value at which URP applies Bloom ... The default value is 0.9." Intensity: "The default is 0, which means that the Bloom effect is disabled." Tint: "select a color for the Bloom effect to tint to." — [URP 17 Manual: Bloom](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/post-processing-bloom.html)
- Color Adjustments. Post Exposure is in EV and applied "after the HDR effect and before tonemapping". Contrast "expand[s] or shrink[s] the overall range of tonal values". Color Filter "multipl[ies] the render and tint[s] the result". Hue Shift "shift[s] the hue of all colors". Saturation "push[es] the intensity of all colors". — [URP 17 Manual: Color Adjustments](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/Post-Processing-Color-Adjustments.html)
- White Balance Temperature: "Higher values result in a warmer color temperature and lower values result in a colder color temperature." — [URP 17 Manual: White Balance](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/Post-Processing-White-Balance.html). Vignette has Color and Intensity ("the strength of the vignette effect"). — [URP 17 Manual: Vignette](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/post-processing-vignette.html)
- 2D Lights. "Global Lights light all objects on the targeted sorting layers", with one global light "per Blend Style, and per sorting layer". Intensity: "The default value is 1." — [URP 17 Manual: 2D light properties](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/2DLightProperties.html). Values above 1 brighten sprites under the Multiply / Multiply with Mask (R) blend styles. Multiply "multiplies the light with the background, which results in a darker color". The 2D Renderer asset holds up to four Light Blend Styles. — summarized from [Unity 6 2D light properties](https://docs.unity.com/en-us/engine/6000.0/manual/unity2d/2d-urp/2d-index/2dlight-properties) and [Light Blend Styles](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/LightBlendStyles.html). Blend Mode options are Additive, Multiply and Subtractive. — [URP 17 Manual: Light Blend Styles](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/LightBlendStyles.html)

### Inferences
- **Computed effect of URP tonemappers on palette colors.** The researcher ported `NeutralTonemap` and the fitted `AcesTonemap` (with `unity_to_ACES` input) from the Unity Graphics repo sources above to a script and ran sRGB hex → linear → tonemap → sRGB. It assumes exposure 0, no other grading, no LUT quantization and no HDR output. Treat the values as indicative to ±2/255.

  | Input | Neutral | ACES |
  |---|---|---|
  | #FF0000 | #D00000 | #CE0008 |
  | #00FF00 | #00D000 | #5AD030 (hue shifts toward yellow, desaturated) |
  | #0000FF | #0000D0 | #0000D1 |
  | #FFFF00 | #D0D000 | #D2CF40 |
  | #FF8000 | #D07F00 | #D2720A |
  | #00FFFF | #00D0D0 | #63D0CE |
  | #FF00FF | #D000D0 | #DB00D0 |
  | #E63946 | #C53B48 | #BC222E |
  | #2A9D8F | #2B978C | #00887A |
  | #F4A261 | #CB9B63 | #CC9253 |
  | #7B2CBF | #7B2EAF | #5C0BA6 |
  | #3A86FF | #3C85D0 | #2171CF |
  | #FFFFFF | #D0D0D0 | #CFCFCF |
  | #808080 | #7F7F7F | #696969 |
  | #404040 | #424242 | #222222 |

  - Neutral leaves mid-tones and darks nearly intact but caps the top end: any channel at 1.0 drops to 0.816 in sRGB (#D0), and mixed hues shift slightly because the curve is per-channel (for example `#3A86FF` becomes `#3C85D0`, bluer-gray). ACES adds a contrast S-curve and hue twists, which makes it a poor fit for categorical palettes. Neither is invertible "for free". To keep both a tonemapper (for HDR glow) and exact palette colors, pre-compensate the palette through the inverse curve. Simpler: keep sprites ≤ 1.0 and choose None.
- With Tonemapping None and HDR on, values above 1.0 (additive sparkles, bloom) hard-clip per channel. Saturated additive effects then clip toward the primaries, or toward white, but stay predictable for in-range palette colors.
- Bloom's default 0.9 threshold is measured on gamma-space brightness. Bright saturated palette colors whose max channel is near 1, such as a yellow `#FFD60A` or `#FF8000`, will bloom and spill their hue onto neighboring tubes and the background. For "true" palette colors, raise the threshold above 1.0 (HDR) so only explicit HDR emissive pixels bloom, or drive bloom through a separate sorting layer or effect.
- Color Adjustments (Saturation, Contrast, Hue Shift, Color Filter), White Balance and Vignette are global transforms applied to every palette color. Any non-default value moves every category. Vignette also makes the same category color differ between screen center and edges, which works against color matching in a sort puzzle.
- The repo has post-processing off on the camera. If it is turned on later with no Volume overrides, a LUT pass still runs (LDR grading, 32³ LUT). LUT interpolation error on saturated colors was not quantified (see Gaps).
- 2D lighting: a Sprite-Lit material shows the design color only when the summed light at that pixel is exactly white at 1.0, for example one Global Light, white, intensity 1, Multiply. Additional point or freeform lights in the same blend style push channels above 1, which clip and desaturate. A colored global light multiplies every category by the same tint and collapses differences, for example a warm light pulls blue and purple toward gray. Custom HLSL shaders that do not sample the 2D light textures (the repo's Liquid, TubeGlass and PourStream shaders appear to be unlit with Universal2D passes) are unaffected by 2D lights. That is the safest choice for palette-critical sprites.

### Gaps
- No source found quantifying URP LUT (32³, LDR mode) interpolation error on saturated colors, or whether an identity LUT is bit-exact.
- The researcher did not verify which URP Neutral and ACES behavior applies under HDR Output (HDR displays); the docs only mention HDR-output-specific Neutral "Hue Shift Amount" and ACES nit presets.
- No official statement found on what lit sprites look like when no Global Light exists in the scene.

## Q3. How does blending a premultiplied transparent glass sprite over a colored background differ in linear vs gamma space, and how can it be compensated?

### Takeaway
In a Linear project, alpha blending happens on linear-light values. A light or white overlay at a given alpha brightens and washes out saturated colors much more than the same layer in Photoshop's default (gamma-encoded) blending, and a dark overlay darkens much less. Matching a Photoshop mock needs roughly half the alpha for light glass (about 0.12 instead of 0.25 over red) and about 1.8× the alpha for dark shading. The mismatch is per-channel and per-background, so no single alpha remap fixes it. Fixes: author in linear (Photoshop "Blend RGB Colors Using Gamma: 1.00"), tune alpha in-engine against the real background, or composite glass-over-liquid inside the liquid shader. Premultiplication must happen in linear space; a texture premultiplied in sRGB is not linear-correct.

### Cited Findings
- "When blending into a framebuffer, the blending occurs in the color space of the framebuffer." Gamma-space blending combines nonlinear colors, which "is not mathematically correct" but is the only option on some hardware. "When you use linear space rendering, blending occurs in linear color space." — [Unity Manual 6000.2: Differences between linear and gamma color space](https://docs.unity3d.com/6000.2/Documentation/Manual/differences-linear-gamma-color-space.html)
- The Texture Import Settings preview "uses gamma blending even if you are working in linear color space", so the import preview does not show in-game blending. — [Unity Manual 6000.2: Linear color space](https://docs.unity3d.com/6000.2/Documentation/Manual/linear-color-space.html)
- Spine forum (Esoteric staff): alpha blending results depend on the color space. A 50% green-over-red blend done in linear comes out much brighter after encoding than the gamma-space blend. Linear is preferred for correct lighting; gamma matches what artists expect from image editors. — [Esoteric Software forum thread 13248](https://en.esotericsoftware.com/forum/d/13248)
- Spine forums: premultiplied-alpha (PMA) atlas textures "are not compatible with linear color space". Unity shows a warning offering two options: re-export without premultiply, or switch to Gamma. The supported Linear workflow is straight alpha with Bleed on export, plus "Alpha Is Transparency" and sRGB enabled on the texture. One user's semi-transparent parts were wrong until sRGB was enabled. — [Esoteric forum: transparent objects in linear](https://ru.esotericsoftware.com/forum/d/26402-transparent-objects-dont-look-correct-in-linear-colour-space), [Esoteric forum: linear vs gamma examples](https://tr.esotericsoftware.com/forum/d/27146-spine-examples-show-different-effect-in-linear-color-space-and-gamma-color-space/13)
- Photoshop: Edit → Color Settings → More Options → "Blend RGB Colors Using Gamma" set to 1.00 makes colors "blend as if they were light rather than ink". The default (off) blends gamma-encoded values; a green stroke on red gets brownish edges with it off and yellowish edges with it on. — [PetaPixel: An Explanation of How Computers Handle Color](https://petapixel.com/2015/03/20/an-explanation-of-how-computers-handle-color). The setting is application-wide, not per document. — [Adobe Community feature request](https://community.adobe.com/t5/photoshop-ecosystem-ideas/photoshop-make-quot-blend-colors-using-gamma-quot-a-document-setting/idc-p/12303598). Users reported bugs at gamma 1.00 in Photoshop 26.10 (Aug–Sep 2025): colors shifting with Move or Zoom, and Pass Through groups changing opacity. — [Adobe Community bug report](https://community.adobe.com/t5/photoshop-ecosystem-bugs/p-photoshop-26-10-incorrect-alpha-blending-on-canvas-for-gamma-1-00-at-different-zoom-levels/m-p/15495532), [Adobe Community: Pass Through groups](https://community.adobe.com/t5/photoshop-ecosystem-bugs/quot-pass-through-quot-groups-don-t-work-in-rgb-gamma-1-00-blending-mode/idi-p/15474990)
- OBS Studio wiki: linear blending fixes "dark artifacts you would normally see where colors would meet" and hue shifts during alpha blending. — [OBS Wiki: Linear Color Blending](https://obsproject.com/wiki/Linear-Color-Blending)

### Inferences
- **Computed gamma vs linear blend examples** (researcher's script; standard sRGB EOTF; `out = a·fg + (1−a)·bg` done on encoded values for "gamma" and on linear values for "linear"; the last column is the linear-space alpha that reproduces the gamma blend's relative luminance):

  | Overlay | Alpha | Background | Gamma blend (Photoshop default) | Linear blend (Unity Linear) | Linear alpha needed to match luminance |
  |---|---|---|---|---|---|
  | #FFFFFF | 0.25 | #E63946 red | #EC6A74 | #ED9094 | 0.117 |
  | #FFFFFF | 0.25 | #2A9D8F teal | #5FB6AB | #8DBCB4 | 0.164 |
  | #FFFFFF | 0.25 | #3A86FF blue | #6BA4FF | #91AFFF | 0.158 |
  | #FFFFFF | 0.25 | #1B1B2F dark bg | #545463 | #8B8B8E | 0.080 |
  | #FFFFFF | 0.15 | #7B2CBF purple | #8F4CC9 | #9973CA | 0.059 |
  | #000000 | 0.30 | #E63946 red | #A12831 | #C42F3A | 0.539 |
  | #000000 | 0.30 | #F4D35E yellow | #AB9442 | #D0B44F | 0.548 |
  | #BFE6FF (bluish glass) | 0.35 | #E63946 red | #D87687 | #D996A8 | 0.166 |

  - A white or light glass layer over liquid is the worst case for a sort-puzzle palette. In linear it pulls every category toward a pastel and reduces chroma differences between categories, and dark backgrounds lift the most (alpha 0.25 behaves like gamma alpha 0.08). Light glass should be much thinner in linear (alpha roughly 0.06 to 0.16 for a mock made at 0.25), or kept off the liquid body and confined to rims and highlights.
  - Dark shading overlays (shadows, inner edges) look weaker in linear, so they need about 1.8× the alpha to match a gamma mock.
- **Premultiplied glass.** With `Blend One OneMinusSrcAlpha`, the shader's rgb is light added on top, and alpha is the fraction of background hidden, both in linear. The sprite's rgb must be premultiplied in linear before sRGB encoding, so the sampler decodes it back to linear premultiplied values. Premultiplying in sRGB (what most image editors and atlas packers do) gives `decode(c·a) ≠ decode(c)·a`, which darkens and shifts semi-transparent texels; that is the reason Spine calls PMA atlases incompatible with Linear. The repo's `make_assets.py` `render_tube` derives alpha and emission from linear EXR renders over black and white and only sRGB-encodes at save time, so it already follows the linear-correct construction. In-engine glass will therefore not match a Photoshop gamma-blended mock, and should not be expected to.
- **Compensation options, from simplest:**
  1. Tune glass `_BodyAlpha`/`_RimAlpha` in-engine against the real liquid colors, not against a Photoshop mock. Or set Photoshop to "Blend RGB Colors Using Gamma 1.00" for mockups so they predict Unity (mind the reported PS 26.10 bugs).
  2. Composite glass-over-liquid inside the liquid shader (the repo's PourStream already has a "_Lighten (matches liquid seen through the glass, linear)" parameter). Then the "seen through glass" color can be designed and checked directly as a final color per category, and the glass sprite only adds rims and highlights.
  3. Do a manual gamma-space blend in the shader: `LinearToSRGB` both layers, lerp, `SRGBToLinear`, output opaque. This needs the background color available in the same shader (true for liquid+glass drawn together), or a grab of what is behind. The URP 2D Renderer's Camera Sorting Layer Texture could provide that, but it was not verified in this session.
  4. Switch the project to Gamma color space (still supported in Unity 6.3/6.4). This changes every blend and lighting result project-wide, so it is not recommended this late.
- Keep straight-alpha sprites (the default Sprite shaders are straight alpha) for ordinary art, and use premultiplied only where the shader is built for it.

### Gaps
- Photoshop's exact default blending math (whether "off" means blending in the document's profile TRC) is not confirmed from an Adobe primary source.
- The URP 2D "Camera Sorting Layer Texture" route for reading the background in a glass shader was not verified against Unity 6 docs here.
- No Unity 6 source found offering a built-in per-material "gamma blending" option for sprites in a Linear project; only the UI vertex-color option above exists.

## Q4. What tools and methods exist for gamut-mapping OKLCH colors into sRGB and for simulating color-vision deficiency on game screenshots? (Includes display differences and a validation workflow.)

### Takeaway
Gamut-map OKLCH to sRGB offline and store the resulting hex as the in-engine source of truth. Use the CSS Color 4 algorithm (binary search on OKLCH chroma with a deltaEOK JND of 0.02 and a clip check, keeping lightness and hue) or Ottosson's adaptive-L0 (α = 0.05), never per-channel clamping. Practical tools: color.js `toGamut()` (CSS method by default), Coloraide, and oklch.com's "closest fallback". For CVD, simulate on sRGB-decoded pixels with Viénot 1999 or Brettel 1997 (dichromacy; Brettel for tritanopia) or Machado 2009 (anomalous trichromacy). Tools: DaltonLens / libDaltonLens, Color Oracle (full-screen), Chrome DevTools "Emulate vision deficiencies" (Machado-based). Avoid Coblis v1. On devices, Unity renders sRGB by default; Samsung OLED "Vivid" mode stretches sRGB content to the panel's wide native gamut, while "Natural" is sRGB-accurate. Test on Natural, and expect players in Vivid to see over-saturated colors.

### Cited Findings
- Ottosson, "sRGB gamut clipping" (25 Jan 2021): per-channel RGB clamping "can lead to unpleasant color distortions" (hue shifts, lost detail). The proposed methods keep hue and project along lines in Oklab toward a lightness-axis point: preserve chroma (keep L, reduce C), project to L=0.5, project to L_cusp, and adaptive L0 (hue independent or dependent). Recommended default: adaptive L0 with α = 0.05. At that α, choosing L0 = 0.5 or L_cusp "seems to matter very little visually", and 0.5 is cheaper (fits a single 2D LUT). — [Björn Ottosson: sRGB gamut clipping](https://bottosson.github.io/posts/gamutclipping/)
- CSS Color 4 "Binary Search Gamut Mapping with Local MINDE". Convert the origin to OkLCh. If L ≥ 100% return white, if L ≤ 0% return black. If in gamut, return it. Otherwise binary-search chroma (epsilon 0.0001); at each step, if the clipped version is within "JND be 0.02" deltaEOK of the current color, return the clipped color. The effect is a MINDE mapping "constrained so the hue and lightness changes are very small". Reference implementations: Coloraide (Python) and color.js (JavaScript). — [W3C CSS Color Module Level 4, §Gamut mapping](https://www.w3.org/TR/css-color-4/#binsearch)
- color.js: `toGamut({space, method})` defaults to the `"css"` method ("finding a chroma value where there is minimal difference between the mapped color and a clipped version"). `"clip"` is "not recommended". The former default `"lch.c"` fails on yellows (much lower chroma than the CSS method). `inGamut()` checks membership. — [Color.js docs: Gamut mapping](https://colorjs.io/docs/gamut-mapping)
- oklch.com (Evil Martians) gives the "Closest fallback (by chroma) in sRGB" for an OKLCH color and can show P3 and Rec2020 gamut boundaries. — [OKLCH Color Picker & Converter](https://oklch.com/)
- Oklab/OKLCH ↔ linear sRGB conversion code is published by the space's author. — [Björn Ottosson: A perceptual color space for image processing](https://bottosson.github.io/posts/oklab/)
- DaltonLens review (19 Oct 2021, updated Nov 2021). For protan and deutan dichromacy, Brettel 1997 and Viénot 1999 are "the clear winners" once adapted to sRGB, and Machado 2009 "consistently ranks lower" (recommend it only for anomalous trichromacy). For tritanopia, Brettel 1997 "is still the most solid and basically only valid choice." Coblis V1 (ColorMatrix) "should never be used"; Coblis V2 "may be ok" but has a restrictive license and little validation. Many implementations "skip the sRGB decoding step altogether", which "makes a whole range of colors look way too dark". Tools: libDaltonLens (public domain C, zero dependencies, unit-tested, with SVG filters), DaltonLens-Python, DaltonLens desktop. Color Oracle uses Brettel for tritanopia and Viénot for protan and deutan. — [DaltonLens: Review of Open Source Color Blindness Simulations](https://daltonlens.org/opensource-cvd-simulation/)
- Chrome DevTools Rendering tab → "Emulate vision deficiencies" (blurred vision, protanopia, deuteranopia, tritanopia, achromatopsia, among others). — [Chrome DevTools: Rendering effects](https://developer.chrome.com/docs/devtools/rendering/apply-effects). Chrome's simulation matrices "are based on a physiologically accurate color vision deficiency simulation model by Machado, Oliveira, and Fernandes"; the deuteranopia `feColorMatrix` row 1 is `0.367 0.861 -0.228`. Puppeteer's `page.emulateVisionDeficiency(type)` enables these programmatically. — [Chrome for Developers: Simulating color vision deficiencies in the Blink Renderer](https://developer.chrome.com/blog/cvd)
- Color Oracle: "a free color blindness simulator for Windows, Mac and Linux" that "applies a full screen color filter to art you are designing, independently of the software in use". Latest version 1.3 (May 5, 2018); the Windows and Linux builds require Java. — [Color Oracle](https://colororacle.org/)
- Unity Player Settings → Color Gamut (iOS and Android pages, 6000.2): "The sRGB gamut is the default (and required) gamut." Gamuts are added with the + button. — [Unity Manual: iOS Player settings](https://docs.unity3d.com/6000.2/Documentation/Manual/class-PlayerSettingsiOS.html), [Unity Manual: Android Player settings](https://docs.unity3d.com/6000.2/Documentation/Manual/class-PlayerSettingsAndroid.html). Older iOS docs (2019.3–2021.1) advise adding DisplayP3 when targeting recent wide-gamut iOS devices. — [Unity 2019.3 iOS Player settings](https://docs.unity3d.com/2019.3/Documentation/Manual/PlayerSettingsiOS-Other)
- Samsung OLED screen modes. DisplayMate measured that the Natural mode sRGB gamut "is an accurate match to the sRGB / Rec.709 Standard Color Gamut" (Galaxy S10 and S20 Ultra). — [DisplayMate: Galaxy S10 color gamuts](https://www.displaymate.com/Gamut_47S.html), [DisplayMate: Galaxy S20 Ultra color gamuts](https://www.displaymate.com/Gamut_52U.html). Samsung describes Vivid as a wide AMOLED gamut with deep primaries, and changed the default from Vivid to Natural on the Galaxy Note10. — [Samsung SG support](https://www.samsung.com/sg/support/mobile-devices/why-does-the-samsung-galaxy-note10-screen-mode-do-not-seem-as-vivid-as-previous-devices/). In 2024, Galaxy S24 owners complained that Vivid was barely more saturated than Natural; Samsung later shipped a firmware fix. — [PhoneArena](https://www.phonearena.com/news/galaxy-s24-owners-are-not-happy-about-dull-and-muted-screen_id154813), [GSMArena](https://m.gsmarena.com/newscomm-61597p2.php)

### Inferences
- **Palette pipeline:** design in OKLCH → gamut-map to sRGB with the CSS method (color.js `toGamut({space:"srgb"})` or Coloraide) → store the sRGB hex in a ScriptableObject or palette asset → feed Unity as sRGB `Color` (Q1 rules). Do not compute OKLCH → sRGB at runtime with plain clamping. If runtime OKLCH math is needed (for example deriving lighter or darker variants per category), port Ottosson's conversion and adaptive-L0 clip to C#.
- Saturated yellows, cyans and greens at high OKLCH chroma are usually out of sRGB. After mapping, check that categories still differ: pairwise deltaEOK well above 0.02 (1 JND), and ideally far larger for a categorical game palette, and also after CVD simulation.
- **Validation workflow (suggested):**
  1. Reference scene: one unlit quad or sprite per palette color, camera post-processing off, opaque. Capture the frame (`ScreenCapture.CaptureScreenshotAsTexture`, or the repo's editor capture trigger) and read pixels at quad centers. Expect ±1/255 from the target hex; larger errors indicate a conversion bug (Q1).
  2. Production scene: sample the same category in its in-game context (liquid behind glass, with lights and any post). Convert the samples and targets to Oklab and report deltaEOK per category. Flag anything above about 0.02–0.04, and check that the minimum inter-category distance survives.
  3. CVD: run the captured screenshots through libDaltonLens or DaltonLens-Python (Viénot for protan and deutan, Brettel for tritan, Machado for anomalous severities), or view them full-screen through Color Oracle, or open the PNG in Chrome with DevTools vision-deficiency emulation. Recompute pairwise deltaEOK on the simulated colors and add non-color cues (symbols, patterns) for pairs that collapse.
  4. Device: check on an sRGB-accurate setting (Samsung "Natural", iPhone default) and on Samsung "Vivid" to see the worst-case over-saturation. Avoid palette pairs that differ only in a hue that wide-gamut stretching pushes together. The palette is authored for sRGB, so P3 and Vivid displays will show it more saturated, not less.
- Because Unity's default gamut is sRGB, OKLCH colors outside sRGB but inside P3 cannot be shown even on P3 phones unless the DisplayP3 gamut is added. That option was not verified for the 2D renderer on Unity 6 (see Gaps), so an sRGB-only palette is the safe default.

### Gaps
- No Unity 6-specific documentation found describing how the DisplayP3 Color Gamut option behaves on iOS and Android with URP 2D: whether sRGB content is color-managed or re-interpreted, or which Android graphics APIs support it.
- No source found on how Android color management handles a Unity app's sRGB surface on Samsung or other OEM "vivid" modes beyond the Samsung and DisplayMate statements above. Newer devices (2025–2026) were not measured in the sources found.
- Not confirmed whether Chrome's current CVD filter decodes sRGB before applying the Machado matrices, which DaltonLens flags as a common accuracy problem.
- Coblis's current algorithm version was not checked directly; its status is taken from the DaltonLens review (2021).
